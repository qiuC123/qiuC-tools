# wxcli 0.4.0 开发复盘：从“已知链接读取”到“可验证的文章发现”

> 复盘日期：2026-08-29
>
> 对应版本：wxcli 0.4.0
>
> 对应提交：`2b9c53a`
>
> 文档目的：解释这次功能是怎样一步步设计出来的、为什么这样设计、遇到了哪些困难，以及哪些方法值得在后续项目中复用。

## 一、这次开发真正解决了什么问题

0.3.0 已经能够在拿到一个明确的微信文章 URL 后读取原文，但它不能回答更前面的问题：

> 不知道文章 URL，只知道“某企业可能发布了校园招聘公告”，怎样找到文章并得到可以信任的微信原文证据？

最初的技术验证证明，外部网页搜索能够找到真实的 `mp.weixin.qq.com/s/...` 链接。但“搜到一个链接”和“确认这是一篇可读取、来源可信的微信文章”不是同一件事。

因此，0.4.0 的核心不是简单增加一个搜索 API，而是建立一条完整的可信链路：

```text
发现可能的链接
→ 只把它当成候选
→ wxcli 严格校验和去重
→ 回读微信原文
→ 提取公众号身份、正文、外链、图片和稳定哈希
→ 形成 Article Evidence
```

这条链路既能被 `official-campus-radar` 调用，也不与招聘业务绑定。校园招聘只是第一个场景，不是 wxcli 的领域模型。

## 二、设计讨论是怎样收敛的

### 1. 先回答“它还算 CLI 吗”

讨论中最先出现的疑问是：wxcli 开始操作网页后，还算不算 CLI？

最终的判断是：CLI 描述的是用户和程序交互的方式，不是程序内部只能做本地计算。Git、curl、云厂商 CLI 都会访问网络，仍然是 CLI。

wxcli 保持以下特征：

- 命令行参数和标准输入是输入边界。
- stdout 在 JSON 模式下只输出一个机器可解析对象。
- stderr 只承载诊断信息。
- HTTP、Chrome、Official API 和本地文件只是 CLI 背后的 Content Provider。
- Chrome 只是必要时显式授权的读取后端，不会变成程序的主界面。

这次讨论沉淀出的经验是：

> 判断一个工具是不是 CLI，要看它的公共交互契约，而不是看它是否访问网页。

### 2. 再划清 wxcli 和招聘雷达的边界

“所有微信有关的都交给 wxcli”一开始仍然过于模糊。经过具体场景追问后，边界被精确为：

wxcli 负责微信内容证据：

- 接收或发现微信文章候选。
- 校验、规范化和去重微信 URL。
- 回读微信原文。
- 提取公众号显示名和公开 `biz_id`。
- 提取正文、图片 URL、外链和稳定哈希。
- 记录验证时间、失败状态和证据来源。

招聘雷达负责招聘业务：

- 搜索和访问企业官网、招聘官网及 ATS。
- 维护企业与公众号的对应关系。
- 判断文章属于哪个企业和招聘批次。
- 提取岗位和申请渠道。
- 将微信证据与官网、ATS 等来源合并。

为什么不把这些业务全部放进 wxcli？

- wxcli 应当服务于不止招聘一个场景。
- 企业、招聘批次和岗位是招聘雷达的业务概念，不是微信文章的固有属性。
- 如果 wxcli 直接写招聘数据库，两边会形成难以拆分的模型耦合。
- 同一篇微信文章可能被多个业务系统以不同方式解释，但原始证据应保持一致。

### 3. 把 Candidate 和 Evidence 分开

这是整个设计中最关键的决定。

外部搜索返回的标题、摘要、日期、公众号提示都可能过期、截断或错误。如果直接把搜索结果转换成 Article，就会把第三方搜索摘要伪装成微信原文。

因此定义了两类不同对象：

- `Article Candidate`：严格校验后的可能文章 URL，仍然不可信。
- `Article Evidence`：wxcli 成功读取微信原文后形成的证据。

失败也不是空 Article，而是明确的 `Hydration Attempt`。

这个决定带来几个直接好处：

- `published_at` 只能来自微信原文，搜索日期只能叫 `backend_date_hint`。
- 搜索 Provider 的来源与内容 Provider 的来源不会混淆。
- 验证页、文章不存在、解析失败可以正常存在于批次结果中。
- 调用方能区分“没搜到”“搜到了但没读到”和“已取得原文证据”。

该决定记录在 [ADR-0004](adr/0004-separate-discovery-candidates-from-article-evidence.md)。

### 4. 明确回读数量，而不是访问所有候选

设计讨论中曾出现“是否要访问全部微信文章”的误解。实际上，wxcli 不会访问全微信，也不会无上限回读所有搜索结果。

最终采用两级策略：

- 排名前 10 的候选必须尝试回读。
- 其余候选只有在账号、公司、标题、日期或来源多样性等理由足够时才选择回读。
- 额外保留少量低置信度样本，用来发现排序盲区。
- 单批最多尝试 20 篇。

这样设计是为了同时控制三件事：

- 搜索覆盖率：不能只看第一两篇。
- 网络和浏览器成本：不能无上限访问。
- 误判风险：低价值候选不应挤占全部回读预算。

这也说明一个通用原则：

> 面对昂贵的验证动作，应明确“必验区、选择区和总预算”，不要只有一个模糊的 limit。

### 5. 二维码和 OCR 为什么推迟到 0.5.0

招聘文章中的二维码可能包含网申入口、社群或小程序信息，因此提取二维码有业务价值。但它不是 0.4.0 搜索发现闭环的必要条件。

二维码和 OCR 会引入新的问题：

- 图片下载、缓存和防盗链。
- 二维码识别失败与多个二维码的语义。
- 图片文字与正文文字的证据边界。
- 二维码目标是否安全、是否允许继续访问。
- 更大的证据包和隐私范围。

因此先完成“候选 → 原文 Evidence”，把二维码、OCR、图片下载和完整证据包留给 0.5.0。这样避免第一次迭代同时承担搜索、浏览器、图像识别和业务分类四类风险。

## 三、最终架构为什么分成两条发现路径

### 1. Direct Discovery：wxcli → Brave

最初设计要求 wxcli 自己具备一个确定、可测试、可替换的 Search Provider，因此实现了 Brave Direct Discovery：

```text
wxcli
→ Brave Discovery Provider
→ Article Candidate
→ Hydration
→ Article Evidence
```

它的优点是：

- 不需要 Agent 参与，调用链固定。
- 查询、分页、cursor、checkpoint 和缓存都由 wxcli 控制。
- 适合只允许普通 API 调用的环境。
- 容易用模拟 Provider 做确定性测试。

它的缺点是搜索策略相对固定，查询扩展能力弱，而且调用者必须另行配置 Brave Key。

### 2. Agent-first：Codex → Agent Reach / Exa → wxcli

后续讨论明确：正式调用方已经愿意把 Codex CLI 当作运行组件，而 Agent 可以进行查询扩展、结果筛选和多轮搜索。于是正式集成调整为 Agent-first：

```text
Codex CLI
→ Agent Reach / Exa
→ schema v1 Candidate Batch
→ wxcli Candidate Ingestion
→ Hydration
→ Article Evidence
```

这里没有把 Exa 直接塞进 wxcli。原因是：

- Exa 是 Agent 运行环境的 External Discovery Provider。
- wxcli 不应依赖 Agent Reach 的安装路径、mcporter 配置或 Exa 凭证。
- Agent 擅长变化快的搜索策略；wxcli 擅长稳定的 URL 和证据校验。
- 如果未来更换 Exa，wxcli 的 Candidate Batch 和 Evidence 契约不需要变化。

这形成了一条重要的信任边界：

> Agent 可以提出候选，但不能宣布候选已经成为证据。

Candidate Batch 因此采用严格 schema、数量和体积上限，拒绝未知字段、凭证、认证头、调用方伪造的发布时间和 Evidence。浏览器授权也不能写进 JSON，只能由本地 CLI 的 `--browser` 参数明确授予。

该决定记录在 [ADR-0005](adr/0005-use-agent-orchestrated-discovery-as-primary-integration.md)。

### 3. 为什么两条路径都保留

Agent-first 和 Direct Discovery 不是两个互相竞争的产品，而是两种运行环境：

- 有 Agent 的正式集成：优先 Agent-first / Exa。
- 没有 Agent、需要确定性 API 的环境：可以使用 Brave Direct Discovery。

两条路径最终都进入同一个 Candidate、Hydration 和 Evidence 模型，因此后半段的可信处理不重复。

## 四、实现中的关键设计

### 1. Provider 分层

旧代码中的 Provider 实际承担“读取内容”的职责，所以领域词汇被精确为 `Content Provider`。搜索则使用独立的 `Discovery Provider`。

两者不能合并，因为：

- Search Provider 只知道索引中的提示。
- Content Provider 才读取微信原文。
- 两者具有不同的凭证、缓存、错误和可信度。
- 合并后很容易把搜索摘要当成正文。

代码保留旧 `Provider` 枚举和公共 Article JSON，避免破坏 0.3.0 调用方；领域文档则使用更精确的名称。这是在“模型变清楚”和“兼容旧接口”之间做的折中。

### 2. 严格 URL 身份和去重

微信文章可能以 token URL 或查询参数 URL 出现，还可能带不同的跟踪参数。如果只按完整字符串去重，同一篇文章会被重复回读。

0.4.0 使用稳定 `article_identity`：

- token URL 使用 token。
- 查询式 URL 使用 `__biz + mid + idx`。
- 缺失 `idx` 时按 1 处理。
- 忽略无关跟踪参数。
- 搜索包装链接和离开 `mp.weixin.qq.com` 的跳转直接拒绝。

同时保留经过严格校验的 `fetch_url` 供实际读取。这样把“长期身份”和“本次访问地址”分开了。

### 3. 时间字段分离

系统中至少存在三种不同时间：

- `discovered_at`：wxcli 什么时候看见这个候选。
- `published_at`：文章原文声明的发布时间。
- `last_verified_at`：wxcli 最近一次成功回读原文的时间。

搜索后端提供的日期只能是 `backend_date_hint`。

如果把这些时间合并成一个 `date` 字段，调用方无法判断它表示发布、发现还是验证，也无法正确实现增量发现和证据新鲜度。

### 4. Cursor、Checkpoint 和缓存分离

- `Search Cursor` 只续同一次查询的下一页。
- `Discovery Checkpoint` 用于以后重复同一查询时找出新候选。
- 15 分钟搜索缓存降低重复 API 调用。
- 180 天候选历史支持增量发现。

cursor 和 checkpoint 都绑定 schema、Provider 和查询指纹。损坏、跨 Provider 或跨查询复用会被拒绝。

这里的经验是：

> “下一页”和“下次只看新增”看起来都像 continuation，但业务语义完全不同，不能共用一个游标。

### 5. Evidence 哈希

`content_sha256` 对文章中相对稳定的内容做规范化 JSON 哈希，包括标题、正文、作者、发布时间、公众号身份、外链和图片 URL。

`evidence_sha256` 再加入证据 schema、提取器版本和身份判断。

发现时间、验证时间和搜索排名不进入稳定哈希，否则同一篇未变化的文章每次读取都会产生不同指纹。

### 6. 部分成功是一等结果

批量搜索成功后，某一篇遇到验证页、文章不存在或解析失败，不应让整个批次失去其他成功证据。

因此：

- 搜索后端整体失败使用非零退出码。
- 搜索成功但部分 Hydration 失败，批次仍可退出 0。
- 结果通过 `summary.partial` 和每篇 `HydrationAttempt` 表达失败。
- 单篇 `article evidence` 失败仍使用明确的非零退出码。

这使调用方能够保存成功证据、安排失败项重试，而不是因为一篇文章让整个日批次回滚。

## 五、遇到的主要困难与解决方式

### 困难 1：微信没有完整文章搜索 API

问题：无法合理承诺全量、实时或官方搜索。

解决：把能力命名为 WeChat Article Discovery，而不是“微信搜索”或“全微信索引”；使用外部搜索发现候选，再由 wxcli 回读微信原文。所有输出都保留搜索 Provider 和内容 Provider 来源。

经验：当上游数据源不完整时，不要用模型或产品文案掩盖不确定性，应在领域对象中直接表达“候选”。

### 困难 2：Brave、Exa、Agent Reach 和 Codex 的职责混淆

问题：讨论一度把“wxcli 自带 Search Provider”和“Agent 使用的外部搜索能力”混为一谈，也产生了是否必须配置 Brave Key、Exa 是否使用匿名额度等疑问。

解决：定义三种角色：

- Search Orchestrator：Codex。
- External Discovery Provider：Agent Reach 使用的 Exa。
- Discovery Provider：wxcli Direct Discovery 使用的 Brave。

最终验收明确记录实际 Provider：搜索仅 Exa，内容仅显式授权的 Chrome；Brave 未使用，匿名 fallback 未使用。Exa Key 属于 Agent 环境，wxcli 不读取、不保存。

经验：不要只说“Provider”，要给每类 Provider 加上职责前缀，并在输出中保留透明的 provenance。

### 困难 3：微信验证页使 HTTP 读取不稳定

问题：真实测试中，多数候选通过 HTTP 都返回 `VERIFICATION_REQUIRED`。

解决：

- HTTP 始终是第一层、低成本读取。
- 没有 `--browser` 时绝不启动 Chrome。
- 用户明确授权后，验证页才串行回退到可见 Chrome。
- Chrome 使用 wxcli 独立 profile，不使用日常浏览器 Cookie。
- 测试前后读取 Chrome 进程快照，证明未授权时没有启动，结束后没有残留。

经验：浏览器不是普通重试机制，而是一种需要单独授权的能力升级。授权必须来自命令边界，不能藏在输入数据中。

### 困难 4：测试通过不等于 Evidence 真的有内容

问题：第一次打包版真实验收中，19 份成功 Evidence 里有一份正文为空、图片也为空，但解析器仍把它视为成功。原因是解析器只检查了 `#js_content` 节点存在，没有检查是否提取到有意义的内容。

解决：

- 增加“正文为空且图片为空则返回 `PARSING_ERROR`”的语义校验。
- 保留图片型文章：正文为空但存在图片时仍允许形成 Evidence。
- 增加两个回归测试，分别覆盖空文章壳和图片型文章。
- 用原问题 URL 重新测试，确认退出码为 8、错误码为 `PARSING_ERROR`。
- 再跑混合批次，确认坏文章结构化失败、好文章继续成功。
- 最后重跑完整 Agent-first 测试，确认 15 份成功 Evidence 中空成功数量为 0。

经验：

> 验收不能只检查 `ok: true` 和对象数量，还要检查产物是否满足业务上的“有用性不变量”。

### 困难 5：开发环境成功不代表打包 EXE 成功

问题：早期真实测试使用 `.venv`，但 PyInstaller 可能改变 Playwright 收集、keyring backend、控制台编码和资源路径。

解决：所有最终真实验收都改为显式指定稳定安装目录中的打包 EXE：

```text
%LOCALAPPDATA%\Programs\wxcli\current\wxcli.exe
```

同时增加打包离线 smoke 和两个独立 live smoke 脚本，真实搜索、微信回读和 Chrome 各自需要不同的 `-Allow*` 开关。

经验：对需要打包交付的 CLI，开发环境测试和交付物测试是两套不同的验收，不能互相替代。

### 困难 6：构建新版本可能先删除正在服役的旧版本

问题：原构建脚本会删除整个 `dist\release`，如果 0.4.0 构建中途失败，PATH 指向的 0.3.0 也会被删除。

解决：

- 构建只清理 `build\release` 和本次 staging。
- 不触碰其他版本产物。
- 同版本目录或 ZIP 已存在时默认报错。
- 只有显式 `-Force` 才删除该版本自己的产物。

经验：发布脚本必须遵守“先产出并验证新版本，再切换旧版本”的顺序。构建失败不应破坏现有服务。

### 困难 7：PATH 指向带版本号的开发目录

问题：每次升级都要修改 PATH；构建或清理开发目录还可能让命令失效。

解决：新增稳定安装根：

```text
%LOCALAPPDATA%\Programs\wxcli\current
```

安装时复制到 `current.new`，完成冒烟测试后通过 NTFS 目录改名切换；旧版本改名为 `previous`。回滚通过三次改名对称交换，并恢复对应 Skill 快照。

经验：PATH 应指向稳定入口，不应指向版本化构建产物。升级和回滚是安装系统的职责，不是用户手工改 PATH 的职责。

### 困难 8：程序升级了，但 Agent 仍读旧 Skill

问题：仓库中的 Skill 已更新，用户级 `%USERPROFILE%\.agents\skills\wxcli` 仍可能停留在旧版，导致 Agent 不知道 discovery 命令或继续使用旧安全规则。

解决：安装脚本同步完整 Skill，并写入 `.wxcli-version`；每个程序版本还保存独立 Skill 快照，回滚程序时一并恢复。

经验：面向 Agent 的产品不仅有二进制版本，还有“操作知识版本”。两者必须一起安装和回滚。

### 困难 9：工作区混入一次性产物

问题：预览目录共占用较大空间，一次性脚本还含个人绝对路径。如果直接 `git add -A`，容易把本地数据带进版本库。

解决：

- 用 `.gitignore` 忽略统一命名的预览目录。
- 删除不可复用的一次性工具脚本。
- 按 discovery、Provider 修复、文档发布契约和安装安全分成语义提交。
- 构建前要求干净工作区。

经验：提交边界和产物卫生不是发布前的小事，它们决定了版本是否可审查、可回溯和可重建。

### 困难 10：凭证存在，但不能为了验证而泄露凭证

问题：需要确认 Exa 或 Brave 是否配置、实际用了哪个 Provider，却不能输出 Key。

解决：

- 只检查“是否存在”和绑定方式，不打印值。
- keyring 状态命令只返回是否配置。
- 扩展统一脱敏器识别 API Key 和订阅头字段。
- Candidate Batch 明确拒绝凭证字段。
- 验收后用“精确值是否出现在产物中”的布尔检查扫描文件，只报告泄漏数量，不回显 Key。

经验：凭证验证应证明“配置和使用关系”，而不是证明“我看到了密钥内容”。

## 六、测试策略为什么分层

### 1. 普通 CI：完全离线

普通测试不访问真实微信或搜索服务，使用：

- 脱敏搜索 fixture。
- 模拟 Discovery Provider。
- 模拟 Article / wxcli 输出。
- 临时 SQLite 和 fake credential backend。
- URL、cursor、checkpoint、缓存、排序、回读和错误码的边界测试。

最终结果：

```text
208 passed
mypy: 35 个源码文件零问题
```

离线测试保证快、稳定、可重复，也避免 CI 触碰真实账号和浏览器。

### 2. 构建 smoke：验证交付物结构

打包 smoke 验证：

- `--version`
- JSON 版本输出
- 默认 `doctor` 不做 live check
- discovery 帮助和凭证状态契约
- ZIP、VERSION 和 SHA-256

它不调用真实搜索或微信。

### 3. 人工 live smoke：验证真实世界

真实测试拆成独立授权：

- `AllowLiveAgentSearch` 或 `AllowLiveSearch`：允许真实搜索。
- `AllowLiveWeChat`：允许只读回读微信。
- `AllowBrowser`：允许启动可见 Chrome。

这三个权限不能互相推导。允许搜索不等于允许访问微信，允许微信 HTTP 不等于允许启动浏览器。

### 4. 对抗审查：验证“系统声称的”和“实际发生的”一致

验收不仅看结果，还检查：

- 未授权前后是否出现 wxcli Chrome 进程。
- 输出实际标明了哪个 Search Provider 和 Content Provider。
- 是否发生未配置的静默 fallback。
- JSON 是否始终是一份可解析对象。
- 部分失败是否保留其他成功 Evidence。
- 成功 Evidence 是否真的包含正文或图片。
- API Key 是否出现在验收产物中。
- 最终测试是否使用打包 EXE 而不是 `.venv`。

这一步直接发现了空 Evidence 缺陷，也证明对抗审查不是重复跑测试，而是检查设计承诺是否被真实运行满足。

## 七、这次最重要的经验

### 经验 1：先定义可信度，再定义字段

如果不先区分 Candidate 和 Evidence，任何字段都可能被错误赋予权威性。先问“这个事实来自哪里、可信到什么程度”，再决定模型应该有什么字段。

### 经验 2：灵活的 Agent 必须接在严格边界之前

Agent 适合扩展查询、尝试不同搜索策略，但不适合直接生成事实证据。Agent 输出应进入一个严格、限量、拒绝未知字段的 ingestion 边界。

### 经验 3：权限是一种本地能力，不是输入数据

Candidate JSON 不能携带 `allow_browser: true`。否则外部数据就能诱导程序打开浏览器。高权限动作必须由用户在本地命令边界显式授权。

### 经验 4：失败应被建模，不应被隐藏

验证页、解析失败、文章不存在都不是“没有对象所以丢掉”。`HydrationAttempt` 让失败可观察、可统计、可重试，也防止系统伪造空 Article。

### 经验 5：发布链路也是产品代码

一个功能只有在打包、安装、PATH、Skill、升级和回滚都工作时才算真正完成。构建脚本删除旧版本、Skill 不同步或 PATH 易断，都属于交付阻断问题。

### 经验 6：真实测试要寻找语义错误

测试数量和类型检查只能证明已写规则下的正确性。真实网页会出现“DOM 节点存在但内容为空”这类未建模情况。验收必须包含业务不变量，例如：成功 Evidence 至少有正文或图片。

### 经验 7：把 Provider 透明性当成公共契约

用户和下游程序应知道候选来自 Exa 还是 Brave，原文来自 HTTP 还是 Chrome。静默 fallback 会破坏成本、安全和可解释性，应当被视为缺陷。

### 经验 8：文档先行适合高边界、高风险功能

本次先通过多轮追问冻结术语、职责、回读预算、浏览器授权和版本拆分，再写 ADR 和设计文档，减少了源码实现阶段反复改模型的成本。

## 八、如果重新做一次，可以更早做什么

1. 更早确认正式运行架构是否允许依赖 Codex CLI。这样可以一开始就明确 Agent-first 与 Direct Discovery 的主次。
2. 在解析器验收标准中提前加入“成功产物有实际内容”的不变量，而不仅检查 DOM 节点和 schema。
3. 在功能开发开始时就设计稳定安装目录、回滚和 Skill 同步，不等到发布审查才补最后一公里。
4. 从第一版文档起就把 Brave 标注为 Direct Discovery 专用，避免用户误以为 Agent-first 也必须配置 Brave。
5. 在真实 smoke 脚本中直接内置 Provider 白名单、空 Evidence 和凭证泄漏检查，使人工验收更自动化。

## 九、可复用的开发检查表

### 领域与边界

- [ ] 搜索命中与原始证据是否是不同对象？
- [ ] 每个关键字段的来源和可信度是否明确？
- [ ] 工具领域与调用方业务领域是否解耦？
- [ ] 外链是只提取、交接，还是允许继续访问？
- [ ] 失败是否有独立模型？

### Agent 与外部输入

- [ ] Agent 是否只能提交候选，不能提交证据结论？
- [ ] 输入是否有 schema、数量和体积限制？
- [ ] 是否拒绝未知字段、凭证和权限开关？
- [ ] 实际 Provider 是否出现在 provenance 中？
- [ ] 是否禁止静默切换未配置 Provider？

### 网络和浏览器

- [ ] 默认路径是否使用最低权限、最低成本 Provider？
- [ ] 浏览器是否需要独立显式授权？
- [ ] 是否使用独立 profile，而不是日常 Cookie？
- [ ] 验证页是否结构化表达，而不是尝试绕过？
- [ ] 批量操作是否有单篇和整批超时？

### 测试和验收

- [ ] 普通 CI 是否完全离线？
- [ ] 是否覆盖重复 URL、非目标 URL、无日期、转载和部分失败？
- [ ] 是否对打包产物运行测试？
- [ ] 是否检查成功产物的业务不变量？
- [ ] 是否比对浏览器进程和 Provider 透明性？
- [ ] 是否扫描凭证泄漏而不打印凭证？

### 发布和运维

- [ ] 构建失败是否不会影响正在服役的旧版本？
- [ ] PATH 是否指向稳定目录？
- [ ] 升级是否先验证再原子切换？
- [ ] 是否保留可验证的 previous 版本？
- [ ] Agent Skill 是否与程序版本一起安装和回滚？
- [ ] Git 是否干净、有 tag、有可回溯的发布提交？

## 十、最终评价

wxcli 0.4.0 的价值不只是增加了“搜索微信文章”的命令，而是把一个不稳定、非官方、容易混淆来源的网页搜索过程，转化成了边界明确、可审计、可部分失败、可供其他程序消费的证据管道。

这次开发最值得保留的方法可以概括为：

```text
先把领域边界说清楚
→ 把不可信候选和可信证据分开
→ 让 Agent 负责灵活发现，让 CLI 负责严格校验
→ 把授权、失败和 Provider 来源显式建模
→ 用离线测试保证稳定，用打包版真实测试发现语义漏洞
→ 把构建、安装、Skill 和回滚纳入“功能完成”的定义
```

当前完成状态、安装信息和后续发布事项见根目录 [`HANDOFF.md`](../HANDOFF.md)。
